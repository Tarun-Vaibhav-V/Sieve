How Sieve works · methods

Route every segment of a prompt into one of three lanes.

A chat model has one fixed context window, shared by what you send and what it writes back. Real conversations waste that window in three ways: verbose text, static text resent every turn, and bulky material kept in full when it is rarely needed. Sieve sits between the chat and the model, splits each request into segments, and gives each segment the cheapest treatment that keeps the answer intact.

Claim under test

A per-segment routing policy across compress / cache / externalize reduces prompt tokens and increases context headroom with accuracy preserved, while a ledger/epoch mechanism controls the KV-prefix invalidation that compression causes.

The three lanes

One lane per segment

COMPRESS

Shorten what must be sent

LLMLingua-2 drops low-information tokens on the CPU. The keep-ratio is chosen per segment from 0.3, 0.5, 0.7, 0.9 or 1.0. A rule-based verifier checks that numbers, IDs, dates, names, and the words around them, survived; if not, the segment is re-compressed at a gentler ratio.

CACHE

Keep static text byte-identical

System prompts, pinned documents and exact repeats are never re-compressed. They sit at the front of the prompt so the server's KV cache can skip them. A document pasted twice becomes a one-line back-reference.

EXTERNALIZE

Move bulky, old text out

The segment is replaced by a short deterministic stub with a summary and up to five key entities. The full text sits in a store. The model can read it back through an expand_context tool call, or Sieve prefetches it when it clearly matches the question.

The KV-cache problem

Compression and caching fight. The ledger referees.

A local server like Ollama keeps the attention state (KV cache) of the last prompt. If the next prompt starts with the same tokens, it skips recomputing them. Compression breaks this: if turn 5 compresses an old message differently from turn 4, every token after that point has to be prefilled again.

Sieve's ledger records the exact string emitted for every segment. On later turns it replays those strings byte-for-byte and routes only the new segments. Compression is memoized on (content hash, ratio, compressor version), so the same input always yields the same string.

A full re-route, an epoch, happens only when the projected prompt plus the 256-token output reserve would pass 80% of the 4096-token window. The allocator then aims at 85% of that line, so the next turns do not re-trigger it.

Measurement detail. On Ollama 0.32.15 (llama-server backend), prompt_eval_count reports the whole prompt even on a cache hit. Sieve therefore estimates reuse from prefill time: it fits cold prefill time against prompt length from novel prompts, then takes reuse = 1 − observed ÷ predicted cold time. The cachetest above validates the method: 95% reuse when nothing changed, about 8% when the change sits 10% of the way in.

The router

Rules first, then a cost-aware classifier

Each segment not claimed by a rule gets 16 features: the original six (is_system, is_last_turn, token count, recency in turns, repeat count, similarity to the current question by MiniLM) plus kind one-hots, digit density, near-duplicate score and prior expansion count.

A gradient-boosting model gives lane probabilities. Sieve picks the lane with the lowest expected cost, not the most likely one. Hiding a segment that is needed costs 5; other mistakes cost 1. A random forest chooses the compression ratio, snapped to a bucket and floored per kind (documents 0.3, chat 0.4, instructions 0.9).

Training data comes from 6 generator seeds that are disjoint from the benchmark seed. Labels come from the workload's ground truth (oracle) or from the hand-written heuristic. Splits are by conversation, never by segment.

Experimental design

How the benchmark is built

Workloads. 76 conversations generated from seed 7. Every entity is invented (codenames, people, figures), so the model cannot answer from memory. Filler text comes from a template grammar that contains no digits and no invented names, so a gold fact can only be found in the messages that ground truth says hold it.

Evaluation points. Each conversation has 1–4 questions. After a question is answered, the scripted gold answer is appended, so a wrong answer never leaks into later turns. Question types: decision_recall (20), lookup_name (64), lookup_number (67), multi_hop (9), negation (4), unanswerable (8), value_update (8).

Protocol. One full pass per condition, never interleaved. The model is unloaded and warmed up before each pass. The first question of every conversation is cold (a novel prompt after a fresh load); later ones are warm. Temperature 0, seed 0, think: false, num_ctx 4096, num_predict 64.

Scoring. Normalized containment for names, exact integer match for numbers, all of day, month and year for dates, first yes/no word for yes/no questions, and a refusal pattern for unanswerable ones. Differences against C0 are paired by question, with 95% bootstrap intervals (2,000 resamples).

  • The plan targeted Qwen3.5-9B on a 6 GB RTX 4050 with partial CPU offload. This run used qwen3:14b on an Apple M5 Pro, fully on the GPU.
  • Prefix reuse is timing-derived, because this Ollama build does not lower prompt_eval_count on a cache hit.
  • With thinking off, the model rarely calls tools unprompted. Sieve adds one line to the final message listing up to six stubs and their keys. It sits in the tail, so the cached prefix is untouched.
  • The verifier also checks the words around each fact. LLMLingua was seen keeping a name while dropping “product lead”.

Limitations

  • Synthetic, small-scale benchmark on one model and one machine. The results describe this suite, not real conversations.
  • Stub summaries are extractive; attachments are text only (OCR and audio are disabled stubs).
  • Oracle labels are partly a function of the features, so classifier F1 is not evidence on its own.
  • Warm-cache baselines are strong: a raw prompt whose prefix is already cached is cheap to extend.
  • The partial-offload regime of the original 6 GB target was not exercised.
